PHASE 1: DETERMINISTIC PHYSICS, COLLISION MODES & SNAPSHOTS
Status: COMPLETED [x]
================================================================================
Goal: Ensure that physics simulations on client and server run at identical fixed 
intervals and resolve collisions deterministically without high-speed tunneling.

Tasks Completed:
  [x] 1.1 Fixed 60Hz Timestep Loop
      - Simulation advances strictly in fixed increments: fixedDt = 1 / 60s (~16.667ms).
      - Time accumulator prevents spiral of death on tab unfocus.

  [x] 1.2 Modular Collision Resolver (src/engine/physics/CollisionResolver.ts)
      - Discrete TOI Rollback: Overlapping colliders are rolled back along relative 
        velocity path to the exact fraction of tick (alpha) of tangent contact.
      - Continuous Swept (CCD): Quadratic swept circle-vs-circle and circle-vs-wall 
        solver prevents high-speed bullet/rock tunneling.
      - Dynamic Adaptive Policy: Automatically promotes bodies from discrete to 
        continuous when displacement (v * dt) exceeds threshold (default: 0.50x radius).
      - Pairwise Continuous Supersession: If either body in a pair is Continuous, 
        the pair resolves via Continuous Swept.
      - Two-tier altitude gating: z < wallHeight vs z >= wallHeight.
      - Massless vs. Massive momentum transfer and roll angular coupling preserved.

  [x] 1.3 Deterministic State Snapshot Engine (src/engine/physics/Snapshot.ts)
      - SnapshotManager.capture(): Serializes tick number, entity positions (x, y, z), 
        linear velocity (vx, vy), vertical velocity (vz), roll angular velocity, 
        heldBy connections, and climbing flags.
      - SnapshotManager.apply(): Restores exact world state from snapshot.
      - SnapshotManager.hasDivergence(): Compares snapshots within configurable deadzones.

  [x] 1.4 Visual Diagnostics & Contact Decay (src/engine/Renderer.ts)
      - 1.2s smooth contact decay: contact pip, expanding ripple, 30px normal vector arrow.
      - Forward swept volume (capsule) lookahead with fill and side rails.
      - Entity status rings and floating badges ([CCD] cyan, [TOI] emerald).
      - Bottom-right corner Collision Diagnostics HUD card.

  [x] 1.5 Verification Test Suites
      - scratch/test_phase_a_collisions.ts: 100% passed.
      - scratch/test_rigidbody_module.ts: 100% passed.

PHASE 2: CLIENT CIRCULAR HISTORY RING BUFFER & LOCAL ROLLBACK HARNESS
Status: COMPLETED [x]
================================================================================
Goal: Equip the client with the memory and capability to rewind physical state 
into the past and re-simulate forward deterministically.

Core Concept:
  The client stores a circular ring buffer of recent ticks (default: 60 ticks / 1.0s,
  dynamically resizable live from 15 to 120 ticks), with a hard rollback clamp of 
  30 ticks (~500ms) to ensure re-simulation never causes frame stutter.
  Each entry contains:
    1. The deterministic physical snapshot of all entities at Tick T.
    2. The local player's input packet applied at Tick T.

Tasks Completed:
  [x] 2.1 StateHistoryBuffer Class (src/engine/physics/StateHistoryBuffer.ts)
      - High-performance circular ring buffer (O(1) indexing by `tick % capacity`).
      - Configurable capacity (default 60 ticks / 1.0s; max rollback limit: 30 ticks / 500ms).
      - Live dynamic capacity resizing (`setCapacity`) preserving recent frames.
      - Push and retrieval methods (`push`, `get`, `getOldestTick`, `getLatestTick`, `getCount`, `clear`).

  [x] 2.2 Client Rollback & Resimulation Engine (src/engine/GameLoop.ts & PlayerManager.ts)
      - Recorded player inputs per tick via `PlayerManager.capturePlayerInputs()`.
      - Replayed inputs deterministically via `PlayerManager.applyPlayerInputs()`.
      - `simulateRollbackTest(ticksBack)`: rewinds to target tick, replays recorded 
        inputs forward, and verifies 0.0000u bit-level divergence against original present state.
      - `injectPerturbationTest(ticksBack)`: demonstrates client-side prediction 
        reconciliation when a past perturbation is corrected.

  [x] 2.3 Interactive DevPanel Rollback Test Tool (src/ui/DevPanel.ts & src/engine/Renderer.ts)
      - Live State History Buffer & Rollback Replay card with real-time status badge.
      - Buffer capacity slider (15 to 120 ticks) with live dynamic resizing.
      - Rollback depth slider (5 to 60 ticks, clamped to maxRollbackTicks).
      - "⏪ Rollback & Verify Replay" test button with pass/fail banner.
      - "🔀 Inject Past Desync & Re-simulate" test button.
      - Diagnostics HUD card on canvas displaying live `Buffer: N/M (X.Xs)`.

  [x] 2.4 Headless Automated Rollback Verification Script
      - scratch/test_phase_2_history_rollback.ts: 100% passed (ring buffer lifecycle,
        live dynamic capacity resizing, 30-tick rollback replay with 0.0000u divergence,
        and past perturbation divergence verification).

PHASE 3: ACTIVE ISLANDS OF INFLUENCE & SLEEPING FREEBODY OPTIMIZATION
Status: COMPLETED [x]
================================================================================
Goal: Prevent rolling back 50+ dormant rocks, food items, and crates across the 
entire arena. Only entities actively influenced by a player are rolled back.

Core Concept:
  - Sleeping Freebodies: Any freebody resting on ground/surface with velocity ~ 0 
    is marked Sleeping. Sleeping bodies take 0 CPU during prediction rollback.
  - Active Island: A connected subgraph of interacting entities (e.g., Player A 
    holding Rock 1, which hits Crate 2). Only entities in this island are 
    rewound and re-simulated during a prediction rollback.

Tasks Completed:
  [x] 3.1 Sleeping Body State Flags (src/engine/GameObject.ts)
      - isSleeping: boolean (default false).
      - sleepTimer: number (ticks with speed < 0.02 u/s and angularSpeed < 0.05 rad/s).
      - After 15 resting ticks (~0.25s), entity enters Sleep.
      - Wakes up immediately upon:
        - External collision impulse.
        - Player grab, throw, or touch.
        - Elevation change or external velocity change.

  [x] 3.2 Island of Influence Graph (src/engine/physics/IslandManager.ts)
      - Group entities into active clusters based on:
        - Character holding/dragging freebodies.
        - Contact points during collision resolution.
      - Disband islands when bodies separate and come to rest.

  [x] 3.3 Selective Island Resimulation
      - During rollback, only update entities belonging to active islands. 
      - Sleeping bodies skip updatePosition and collision checks (0 CPU).
      - SnapshotManager.apply supports selective island filtering.

  [x] 3.4 Diagnostics & Test Suite
      - Bottom-right Diagnostics HUD displays live active islands and sleeping body counts.
      - Headless test suite (scratch/test_phase_3_islands_sleeping.ts) passes 100%.

PHASE 3.5: PSEUDO-SERVER & REMOTE RELAY LOOPBACK TEST HARNESS
Status: COMPLETED [x]
================================================================================
Goal: Run an authoritative pseudo-server simulation alongside the client in the 
same browser tab/instance, routing client inputs and server snapshots through a real 
remote WebSocket relay server (e.g. wss://echo.websocket.org or custom relay).
This provides real internet packet latency and jitter, while rendering both the 
client prediction and authoritative server state overlaid/stacked directly on 
top of each other in real time before creating a standalone headless server.

Core Concept:
  - Dual Simulation in One Process:
    - Client World: Predicts ahead using local inputs immediately.
    - Pseudo-Server World: Runs authoritative physics, consuming inputs that 
      traveled over the real internet relay round-trip.
  - Remote WebSocket Relay Loopback:
    - Client sends input packet -> Remote Relay Server -> Pseudo-Server receives input.
    - Pseudo-Server steps tick -> Sends snapshot -> Remote Relay -> Client reconciles.
  - Stacked Real-Time Visualization:
    - Ghost / outline rendering showing the server's true position vs. client's 
      predicted position simultaneously on screen.
    - Live discrepancy meters (RTT latency, packet loss %, drift delta).

Tasks Completed:
  [x] 3.5.1 In-Tab Pseudo-Server Sim Instance (src/server/ServerGameSimulation.ts)
      - Secondary isolated physics world running deterministic 60Hz loop.
      - Headless Arena, Characters, GameObjects, CollisionResolver, IslandManager.
  [x] 3.5.2 Relay Loopback Networking Channel (src/network/RelayClient.ts)
      - Client streams pc_player_input packets over remote WebSocket relay with zero-drop input batching.
      - Independent 60Hz Server Clock: RelayClient.stepServerPhysics(dt) advances the server simulation 
        at a fixed 60Hz on every frame, decoupled from network packet arrival times (eliminating slow-motion).
      - Echoed packets route into serverSimulation.queueInput() to feed the server's input queue.
      - Movement extrapolation prevents jitter freeze during brief single-frame packet stalls.
  [x] 3.5.3 Stacked Real-Time Dual-Render Mode (src/engine/Renderer.ts)
      - Renders authoritative server ghost with [SERVER SIM (XXms)] pill badge.

      - Live 1-click "🔄 Resync" button instantly re-aligns server entities with client positions.

PHASE 5: CLIENT INPUT STREAMING & SERVER JITTER INPUT QUEUE
Status: IN PROGRESS [/]
================================================================================
Goal: Stream player inputs from client to server reliably, retransmitting critical 
one-shot action commands until acknowledged, and buffer continuous inputs on the 
server to absorb network packet jitter without starvation.

Tasks Completed & Planned:
  [x] 5.1 Reliable Action Commands & Retransmission Pipeline (src/network/RelayClient.ts & StateHistoryBuffer.ts)
      - Critical Action Commands: Picking up, dropping, and throwing objects are 
        classified as high-priority reliable action commands (ReliableActionCommand).
      - Retransmission Outbox: The sender maintains an unacknowledged action outbox 
        (unacknowledgedActions) and retransmits all pending actions with every outgoing packet 
        until delivery confirmation (ACK) is received from the recipient.
      - Server Idempotent Deduplication: The server tracks processedActionIds so duplicate 
        retransmissions are acknowledged without executing duplicate pickups, drops, or throws.
      - Delivery Confirmation (ACK): Recipient echoes back ackActionIds, purging confirmed 
        commands from the sender's retransmission queue.
      - Headless Test Suite (scratch/test_reliable_action_retransmission.ts) passes 100%.

  [ ] 5.2 Server Jitter Buffer (Per-Player Queue)
      - Target depth: 2 ticks of input (~33.3ms buffer).
      - Server holds inputs in a priority queue sorted by tick number.
      - Each tick, the server pops the input corresponding to current simulation tick.
      - Missing Input Handling: If buffer starves, repeat last known input (or zero input).

PHASE 6: ADAPTIVE CLOCK SYNCHRONIZATION & TIME DILATION (CRUISE CONTROL)
Status: PLANNED [ ]
================================================================================
Goal: Maintain a steady 2-tick input buffer on the server by gently speeding up 
or slowing down the client's physics tick rate without hard pauses or stutter.

Tasks to Implement:
  [ ] 6.1 Server Buffer Depth Measurement
      - Every 10 ticks, the server checks the queue depth for each player.
      - Target: 2 frames.
      - Underflow (< 1 frame): Client is running too slow or packets arriving late.
      - Overflow (> 3 frames): Client is running ahead of server.

  [ ] 6.2 Time Dilation Feedback Packet
      - Server sends clock command:
        {
          type: "clock_sync",
          serverTick: number,
          targetQueueDepth: 2,
          currentQueueDepth: number,
          dilationFactor: number  // e.g., 1.01 (speed up 1%) or 0.99 (slow down 1%)
        }

  [ ] 6.3 Client Adaptive Accumulator
      - In `GameLoop.ts`:
        `this.accumulator += deltaSeconds * this.timeDilation;`
      - Clamped range: 0.98x to 1.02x (imperceptible to human eye, keeps audio smooth).
      - Returns to 1.00x once the server buffer stabilizes at 2 frames.

PHASE 8: CLIENT PREDICTION RECONCILIATION & VISUAL SMOOTHING DAMPENER
Status: PLANNED [ ]
================================================================================
Goal: When server snapshots arrive, verify client prediction. If predicted 
state matches within deadzone tolerance, do nothing. If divergence occurred, 
snap physics and smoothly damp visual offset.

Tasks to Implement:
  [ ] 8.1 Snapshot Comparison & Error Deadzones
      - When server snapshot for Tick T arrives:
        1. Look up client's historical snapshot at Tick T in StateHistoryBuffer.
        2. Compare positions: deltaPos = |serverPos - predictedPos|.
        3. Compare velocities: deltaVel = |serverVel - predictedVel|.
      - Deadzone Tolerances:
        - If deltaPos < 0.05 units (~1.8px) and deltaVel < 0.10:
          PREDICTION SUCCESS. Discard history older than Tick T. No action needed.

  [ ] 8.2 Misprediction Correction (Rollback & Fast-Forward)
      - If deltaPos or deltaVel exceeds deadzone (e.g. wall bounce angle mispredicted, 
        or an unexpected collision occurred):
        1. Set visual offset: `visualOffset = predictedPos - serverPos`.
        2. Snap physical entity state to Server State at Tick T.
        3. Re-simulate physics forward from Tick T+1 to currentTick using recorded inputs.
        4. Overwrite history buffer for ticks T+1..currentTick.

  [ ] 8.3 Render Smoothing Dampener (Eliminates Visual Popping)
      - During rendering:
        `drawX = entity.position.x - visualOffset.x;`
        `drawY = entity.position.y - visualOffset.y;`
      - Decay visualOffset smoothly toward zero over 3 to 5 frames (~50ms - 80ms):
        `visualOffset.x *= 0.70;`
        `visualOffset.y *= 0.70;`
      - Result: Physics hitboxes snap instantaneously and remain 100% accurate, 
        while the visible sprite glides smoothly without jitter or teleportation.
