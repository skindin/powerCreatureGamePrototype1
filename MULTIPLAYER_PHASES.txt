PHASE 1: DETERMINISTIC PHYSICS, COLLISION MODES & SNAPSHOTS
Status: COMPLETED [x]
================================================================================
Goal: Ensure that physics simulations on client and server run at identical fixed 
intervals and resolve collisions deterministically without high-speed tunneling.

Tasks Completed:
  [x] 1.1 Fixed 60Hz Timestep Loop
      - Simulation advances strictly in fixed increments: fixedDt = 1 / 60s (~16.667ms).
      - Time accumulator prevents spiral of death on tab unfocus.

  [x] 1.2 Modular Collision Resolver (src/engine/physics/CollisionResolver.ts)
      - Discrete TOI Rollback: Overlapping colliders are rolled back along relative 
        velocity path to the exact fraction of tick (alpha) of tangent contact.
      - Continuous Swept (CCD): Quadratic swept circle-vs-circle and circle-vs-wall 
        solver prevents high-speed bullet/rock tunneling.
      - Dynamic Adaptive Policy: Automatically promotes bodies from discrete to 
        continuous when displacement (v * dt) exceeds threshold (default: 0.50x radius).
      - Pairwise Continuous Supersession: If either body in a pair is Continuous, 
        the pair resolves via Continuous Swept.
      - Two-tier altitude gating: z < wallHeight vs z >= wallHeight.
      - Massless vs. Massive momentum transfer and roll angular coupling preserved.

  [x] 1.3 Deterministic State Snapshot Engine (src/engine/physics/Snapshot.ts)
      - SnapshotManager.capture(): Serializes tick number, entity positions (x, y, z), 
        linear velocity (vx, vy), vertical velocity (vz), roll angular velocity, 
        heldBy connections, and climbing flags.
      - SnapshotManager.apply(): Restores exact world state from snapshot.
      - SnapshotManager.hasDivergence(): Compares snapshots within configurable deadzones.

  [x] 1.4 Visual Diagnostics & Contact Decay (src/engine/Renderer.ts)
      - 1.2s smooth contact decay: contact pip, expanding ripple, 30px normal vector arrow.
      - Forward swept volume (capsule) lookahead with fill and side rails.
      - Entity status rings and floating badges ([CCD] cyan, [TOI] emerald).
      - Bottom-right corner Collision Diagnostics HUD card.

  [x] 1.5 Verification Test Suites
      - scratch/test_phase_a_collisions.ts: 100% passed.
      - scratch/test_rigidbody_module.ts: 100% passed.

PHASE 2: CLIENT CIRCULAR HISTORY RING BUFFER & LOCAL ROLLBACK HARNESS
Status: READY TO IMPLEMENT [ ]
================================================================================
Goal: Equip the client with the memory and capability to rewind physical state 
into the past and re-simulate forward deterministically.

Core Concept:
  The client stores a circular ring buffer of the past 60 ticks (1.0 second), 
  with a maximum rollback clamp of 30 ticks (~500ms) to ensure re-simulation 
  never causes frame stutter.
  Each entry contains:
    1. The deterministic physical snapshot of all entities at Tick T.
    2. The local player's input packet applied at Tick T.

Tasks to Implement:
  [ ] 2.1 StateHistoryBuffer Class (src/engine/physics/StateHistoryBuffer.ts)
      - Fixed capacity array of 60 slots (O(1) indexing by `tick % capacity`).
      - Configurable capacity (default 60 ticks / 1.0s; max rollback limit: 30 ticks / 500ms).
      - Protects framerate: if a packet arrives older than 30 ticks, perform a 
        direct state snap rather than re-simulating excessive frames.
      - Methods:
        - push(tick, snapshot, inputs): store frame data without heap allocations.
        - get(tick): retrieve snapshot and inputs for specific tick.
        - clear(): reset buffer.
        - getOldestTick() / getLatestTick().

  [ ] 2.2 Client Rollback & Resimulation Engine
      - rollbackTo(targetTick):
        1. Restore snapshot from `buffer.get(targetTick)`.
        2. Set currentTick = targetTick.
      - resimulateUpTo(currentTick):
        1. Loop forward from targetTick to currentTick.
        2. Re-apply recorded input for each tick.
        3. Step physics simulation (fixedDt = 1/60s).
        4. Overwrite buffer entries with the newly re-simulated snapshots.

  [ ] 2.3 Interactive DevPanel Rollback Test Tool
      - Button: "⏪ Simulate 30-Tick Rollback" in DevPanel.
      - On click:
        - Captures state now (Tick T).
        - Rewinds 30 ticks into history (Tick T - 30).
        - Re-simulates back to Tick T using historical inputs.
        - Asserts divergence == 0.0000 between original and replayed state.
        - Displays visual green/red pass badge on HUD.

  [ ] 2.4 Headless Automated Rollback Verification Script
      - scratch/test_history_buffer.ts: Automated script testing 1000 steps of 
        movement, throws, and bounces with random 10-tick to 45-tick rollbacks.

PHASE 3: ACTIVE ISLANDS OF INFLUENCE & SLEEPING FREEBODY OPTIMIZATION
Status: PLANNED [ ]
================================================================================
Goal: Prevent rolling back 50+ dormant rocks, food items, and crates across the 
entire arena. Only entities actively influenced by a player are rolled back.

Core Concept:
  - Sleeping Freebodies: Any freebody resting on ground/surface with velocity ~ 0 
    is marked Sleeping. Sleeping bodies take 0 CPU during prediction rollback.
  - Active Island: A connected subgraph of interacting entities (e.g., Player A 
    holding Rock 1, which hits Crate 2). Only entities in this island are 
    rewound and re-simulated during a prediction rollback.

Tasks to Implement:
  [ ] 3.1 Sleeping Body State Flags (src/engine/GameObject.ts)
      - isSleeping: boolean (default false).
      - sleepTimer: number (ticks with speed < 0.01 u/s and angularSpeed < 0.05 rad/s).
      - After 15 resting ticks (~0.25s), entity enters Sleep.
      - Wakes up immediately upon:
        - External collision impulse.
        - Player grab or touch.
        - Elevation change (ground removed or wall deleted).

  [ ] 3.2 Island of Influence Graph (src/engine/physics/IslandManager.ts)
      - Group entities into active clusters based on:
        - Character holding/dragging freebodies.
        - Contact points during collision resolution.
      - Disband islands when bodies separate and come to rest.

  [ ] 3.3 Selective Island Resimulation
      - During rollback, only update entities belonging to the local player's 
        active island. All other entities remain frozen in their current state.

PHASE 5: CLIENT INPUT STREAMING & SERVER JITTER INPUT QUEUE
Status: PLANNED [ ]
================================================================================
Goal: Stream player inputs from client to server reliably and buffer them on the 
server to absorb network packet jitter without starvation.

Tasks to Implement:
  [ ] 5.1 Client Input Packet Specification
      - Packet Schema:
        {
          type: "input",
          playerId: string,
          tick: number,          // The simulation tick this input applies to
          subTickTime: number,   // Client send timestamp for RTT calculation
          moveX: number,         // -1.0 to +1.0
          moveY: number,         // -1.0 to +1.0
          aimX: number,          // Virtual aim cursor x coordinate
          aimY: number,          // Virtual aim cursor y coordinate
          isGrab: boolean,       // Pickup / Swap
          isDrop: boolean,       // Dedicated Drop (Q / Y)
          isThrow: boolean,      // Throw held item (L-Click / RT / RB)
          isJump: boolean,       // Jump / Wall Climb (Space / A)
          isSprint: boolean      // Sprint modifier (Shift / LB)
        }
      - Redundant Past Inputs: Each packet includes current tick input plus 
        the previous 3 tick inputs to survive dropped packets without stalling.

  [ ] 5.2 Server Jitter Buffer (Per-Player Queue)
      - Target depth: 2 ticks of input (~33.3ms buffer).
      - Server holds inputs in a priority queue sorted by tick number.
      - Each tick, the server pops the input corresponding to current simulation tick.
      - Missing Input Handling: If buffer starves, repeat last known input (or zero input).

PHASE 6: ADAPTIVE CLOCK SYNCHRONIZATION & TIME DILATION (CRUISE CONTROL)
Status: PLANNED [ ]
================================================================================
Goal: Maintain a steady 2-tick input buffer on the server by gently speeding up 
or slowing down the client's physics tick rate without hard pauses or stutter.

Tasks to Implement:
  [ ] 6.1 Server Buffer Depth Measurement
      - Every 10 ticks, the server checks the queue depth for each player.
      - Target: 2 frames.
      - Underflow (< 1 frame): Client is running too slow or packets arriving late.
      - Overflow (> 3 frames): Client is running ahead of server.

  [ ] 6.2 Time Dilation Feedback Packet
      - Server sends clock command:
        {
          type: "clock_sync",
          serverTick: number,
          targetQueueDepth: 2,
          currentQueueDepth: number,
          dilationFactor: number  // e.g., 1.01 (speed up 1%) or 0.99 (slow down 1%)
        }

  [ ] 6.3 Client Adaptive Accumulator
      - In `GameLoop.ts`:
        `this.accumulator += deltaSeconds * this.timeDilation;`
      - Clamped range: 0.98x to 1.02x (imperceptible to human eye, keeps audio smooth).
      - Returns to 1.00x once the server buffer stabilizes at 2 frames.

PHASE 8: CLIENT PREDICTION RECONCILIATION & VISUAL SMOOTHING DAMPENER
Status: PLANNED [ ]
================================================================================
Goal: When server snapshots arrive, verify client prediction. If predicted 
state matches within deadzone tolerance, do nothing. If divergence occurred, 
snap physics and smoothly damp visual offset.

Tasks to Implement:
  [ ] 8.1 Snapshot Comparison & Error Deadzones
      - When server snapshot for Tick T arrives:
        1. Look up client's historical snapshot at Tick T in StateHistoryBuffer.
        2. Compare positions: deltaPos = |serverPos - predictedPos|.
        3. Compare velocities: deltaVel = |serverVel - predictedVel|.
      - Deadzone Tolerances:
        - If deltaPos < 0.05 units (~1.8px) and deltaVel < 0.10:
          PREDICTION SUCCESS. Discard history older than Tick T. No action needed.

  [ ] 8.2 Misprediction Correction (Rollback & Fast-Forward)
      - If deltaPos or deltaVel exceeds deadzone (e.g. wall bounce angle mispredicted, 
        or an unexpected collision occurred):
        1. Set visual offset: `visualOffset = predictedPos - serverPos`.
        2. Snap physical entity state to Server State at Tick T.
        3. Re-simulate physics forward from Tick T+1 to currentTick using recorded inputs.
        4. Overwrite history buffer for ticks T+1..currentTick.

  [ ] 8.3 Render Smoothing Dampener (Eliminates Visual Popping)
      - During rendering:
        `drawX = entity.position.x - visualOffset.x;`
        `drawY = entity.position.y - visualOffset.y;`
      - Decay visualOffset smoothly toward zero over 3 to 5 frames (~50ms - 80ms):
        `visualOffset.x *= 0.70;`
        `visualOffset.y *= 0.70;`
      - Result: Physics hitboxes snap instantaneously and remain 100% accurate, 
        while the visible sprite glides smoothly without jitter or teleportation.

PHASE 9: REMOTE PLAYER ENTITY INTERPOLATION & FLIGHT HANDOFF
Status: PLANNED [ ]
================================================================================
Goal: Render other human players and their thrown objects fluidly without jitter.

Tasks to Implement:
  [ ] 9.1 Remote Player Entity Interpolation (Snapshot Interpolation)
      - Maintain a 100ms render buffer of received server snapshots for remote players.
      - Interpolate remote players smoothly between Snapshot N and Snapshot N+1:
        `pos = lerp(snapN.pos, snapN+1.pos, alpha)`
      - Extrapolate up to 50ms with dead reckoning if a packet is momentarily delayed.

  [ ] 9.2 Ballistic Item Flight Handoff
      - While held by local player: 100% locally predicted.
      - Upon throw: Locally predicted along parabolic trajectory.
      - In-flight mid-air collision or contested touch: Reconciles cleanly with 
        server snapshot without losing height-ring or ground shadow integrity.

VERIFICATION CHECKLIST & ACCEPTANCE CRITERIA
================================================================================
To consider Multiplayer fully complete, the following scenarios must pass:

  [ ] 1. High-Speed Throw Consistency:
         Throwing a high-speed ball at a wall reflects with identical trajectory 
         on both client and server without tunneling through the wall.

  [ ] 2. Contested Pick Up Tiebreaker:
         Two players pressing Grab on the same object on the same frame results 
         in one clean pickup without duplicate held objects or desync.

  [ ] 3. Simulated Latency Resilience (50ms - 150ms simulated ping):
         Local character movement, sprinting, jumping, and grabbing feels 
         instantaneous (0ms perceived input lag) with zero noticeable snapping.

  [ ] 4. Time Dilation Stability:
         Under fluctuating ping (jitter), the client accumulator gently dilates 
         by +/-1% without audio/visual stutter or frame freezes.

  [ ] 5. Headless Determinism Test:
         Automated server-client simulation running 5,000 continuous ticks 
         produces identical hash / 0.0000 divergence across all entities.
