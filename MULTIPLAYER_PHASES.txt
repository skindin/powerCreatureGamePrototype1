PHASE 2: CLIENT CIRCULAR HISTORY RING BUFFER & LOCAL ROLLBACK HARNESS
Status: COMPLETED [x]
================================================================================
Goal: Equip the client with the memory and capability to rewind physical state 
into the past and re-simulate forward deterministically.

Core Concept:
  The client stores a circular ring buffer of recent ticks (default: 60 ticks / 1.0s,
  dynamically resizable live from 15 to 120 ticks), with a hard rollback clamp of 
  30 ticks (~500ms) to ensure re-simulation never causes frame stutter.
  Each entry contains:
    1. The deterministic physical snapshot of all entities at Tick T.
    2. The local player's input packet applied at Tick T.

Tasks Completed:
  [x] 2.1 StateHistoryBuffer Class (src/engine/physics/StateHistoryBuffer.ts)
      - High-performance circular ring buffer (O(1) indexing by `tick % capacity`).
      - Configurable capacity (default 60 ticks / 1.0s; max rollback limit: 30 ticks / 500ms).
      - Live dynamic capacity resizing (`setCapacity`) preserving recent frames.
      - Push and retrieval methods (`push`, `get`, `getOldestTick`, `getLatestTick`, `getCount`, `clear`).

  [x] 2.2 Client Rollback & Resimulation Engine (src/engine/GameLoop.ts & PlayerManager.ts)
      - Recorded player inputs per tick via `PlayerManager.capturePlayerInputs()`.
      - Replayed inputs deterministically via `PlayerManager.applyPlayerInputs()`.
      - `simulateRollbackTest(ticksBack)`: rewinds to target tick, replays recorded 
        inputs forward, and verifies 0.0000u bit-level divergence against original present state.
      - `injectPerturbationTest(ticksBack)`: demonstrates client-side prediction 
        reconciliation when a past perturbation is corrected.

  [x] 2.3 Interactive DevPanel Rollback Test Tool (src/ui/DevPanel.ts & src/engine/Renderer.ts)

PHASE 3: ACTIVE ISLANDS OF INFLUENCE & SLEEPING FREEBODY OPTIMIZATION
Status: COMPLETED [x]
================================================================================
Goal: Prevent rolling back 50+ dormant rocks, food items, and crates across the 
entire arena. Only entities actively influenced by a player are rolled back.

Core Concept:
  - Sleeping Freebodies: Any freebody resting on ground/surface with velocity ~ 0 
    is marked Sleeping. Sleeping bodies take 0 CPU during prediction rollback.
  - Active Island: A connected subgraph of interacting entities (e.g., Player A 
    holding Rock 1, which hits Crate 2). Only entities in this island are 
    rewound and re-simulated during a prediction rollback.

Tasks Completed:
  [x] 3.1 Sleeping Body State Flags (src/engine/GameObject.ts)
      - isSleeping: boolean (default false).
      - sleepTimer: number (ticks with speed < 0.02 u/s and angularSpeed < 0.05 rad/s).
      - After 15 resting ticks (~0.25s), entity enters Sleep.
      - Wakes up immediately upon:
        - External collision impulse.
        - Player grab, throw, or touch.
        - Elevation change or external velocity change.

  [x] 3.2 Island of Influence Graph (src/engine/physics/IslandManager.ts)
      - Group entities into active clusters based on:
        - Character holding/dragging freebodies.
        - Contact points during collision resolution.
      - Disband islands when bodies separate and come to rest.

  [x] 3.3 Selective Island Resimulation
      - During rollback, only update entities belonging to active islands. 
      - Sleeping bodies skip updatePosition and collision checks (0 CPU).
      - SnapshotManager.apply supports selective island filtering.

  [x] 3.4 Diagnostics & Test Suite
      - Bottom-right Diagnostics HUD displays live active islands and sleeping body counts.
      - Headless test suite (scratch/test_phase_3_islands_sleeping.ts) passes 100%.

Status: COMPLETED [x]

Tasks Completed & Planned:
  [x] 5.1 Reliable Action Commands & Retransmission Pipeline (src/network/RelayClient.ts & StateHistoryBuffer.ts)
      - Critical Action Commands: Picking up, dropping, and throwing objects are 
        classified as high-priority reliable action commands (ReliableActionCommand).
      - Retransmission Outbox: The sender maintains an unacknowledged action outbox 
        (unacknowledgedActions) and retransmits all pending actions with every outgoing packet 
        until delivery confirmation (ACK) is received from the recipient.
      - Server Idempotent Deduplication: The server tracks processedActionIds so duplicate 
        retransmissions are acknowledged without executing duplicate pickups, drops, or throws.
      - Delivery Confirmation (ACK): Recipient echoes back ackActionIds, purging confirmed 
        commands from the sender's retransmission queue.
      - Headless Test Suite (scratch/test_reliable_action_retransmission.ts) passes 100%.

  [x] 5.2 Server Jitter Buffer (Per-Player Queue) (src/server/ServerJitterBuffer.ts & ServerGameSimulation.ts)
      - Target Depth: 2 ticks of input (~33.3ms buffer) to absorb WAN packet jitter.
      - Priority Queue: Inputs held in PlayerJitterQueue sorted strictly ascending by simulation tick.
      - Out-of-Order & Deduplication: Out-of-order packets correctly inserted into sorted positions;
        duplicate and stale packets (tick <= lastConsumedTick) safely rejected.
      - Each Tick Consumption: Server simulation consumes input corresponding to current simulation tick.
      - Starvation Handling: When queue is empty, returns safe neutral input packet (zero movement velocity
        and all action buttons false to prevent runaway ghost overshoot), while preserving last known aim coordinates.
      - Burst Drainage: When WAN jitter delivers a backlog burst (> 4 ticks), intermediate excess inputs
        are drained and fast-forwarded to keep server input latency tightly locked to 1-2 ticks without lagging.
      - Telemetry Metrics: Exposes currentDepth, targetDepth (2), oldestTick, newestTick, starvations,

PHASE 6: ADAPTIVE CLOCK SYNCHRONIZATION & TIME DILATION (CRUISE CONTROL)
Status: COMPLETED [x]
================================================================================
Goal: Maintain a steady 2-tick input buffer on the server by gently speeding up 
or slowing down the client's physics tick rate without hard pauses or stutter.

Tasks Completed & Implemented:
  [x] 6.1 Server Buffer Depth Measurement (src/server/ServerGameSimulation.ts & ServerJitterBuffer.ts)
      - Every 10 ticks, the server checks the jitter queue depth for each player.
      - Target: 2 frames (~33.3ms buffer).
      - Underflow (< 1 frame): Client is running too slow or packets arriving late; flags speedup.
      - Overflow (> 3 frames): Client is running ahead of server; flags slowdown.
      - Steady (1 to 3 frames): Healthy cruise buffer maintained.

  [x] 6.2 Time Dilation Feedback Packet (src/server/ServerJitterBuffer.ts & ServerGameSimulation.ts)
      - Server sends clock command ClockSyncPacket with snapshot broadcasts:
        {
          type: "clock_sync",
          serverTick: number,
          targetQueueDepth: 2,
          currentQueueDepth: number,
          dilationFactor: number  // e.g., 1.015 (speed up 1.5%) or 0.985 (slow down 1.5%)
        }
      - Strict clamping within [0.980, 1.020] (imperceptible to human eye, keeps physics deterministic).

  [x] 6.3 Client Adaptive Accumulator (src/engine/GameLoop.ts & src/engine/Renderer.ts)
      - In `GameLoop.ts`:
        Smoothly steers current timeDilation toward targetTimeDilation (lerp rate 0.08 per frame).
        `this.accumulator += deltaSeconds * this.timeDilation;`
      - Clamped range: 0.98x to 1.02x (imperceptible to human eye, keeps audio smooth).
      - Automatically returns to 1.000x once the server buffer stabilizes at 2 frames.
      - Visual Diagnostics: Displayed in Canvas Diagnostics HUD as `Cruise Control: 1.000x (2f)`
        and in top-bar telemetry as `Jitter: 2f (1.000x)`.
      - Headless Test Suite (scratch/test_phase_6_clock_sync.ts) passes 26/26 tests (100%).

PHASE 8: CLIENT PREDICTION RECONCILIATION & VISUAL SMOOTHING DAMPENER
Status: COMPLETED [x]
===============================================================================
Goal: When server snapshots arrive, verify client prediction. If predicted 
state matches within deadzone tolerance, do nothing. If divergence occurred, 
snap physics and smoothly damp visual offset.

Tasks Completed:
  [x] 8.1 Snapshot Comparison & Error Deadzones
      - When server snapshot for Tick T arrives:
        1. Identify client's acknowledged input tick: `clientTick = serverSnapshot.lastProcessedInputTick[playerId]`.
        2. Look up client's historical prediction at `clientTick` in StateHistoryBuffer.
        3. Compare positions: deltaPos = |serverPos - predictedPos|.
        4. Compare velocities: deltaVel = |serverVel - predictedVel|.
      - Deadzone Tolerances:
        - If deltaPos < 0.05 units (~1.8px) and deltaVel < 0.15:
          PREDICTION SUCCESS. Prune history older than `clientTick`. Zero rollbacks, zero jitter!

  [x] 8.2 Misprediction Correction (Rollback & Fast-Forward)
      - If deltaPos or deltaVel exceeds deadzone (e.g. unexpected collision or server nudge):
        1. Set visual offset: `visualOffset = postPos - prePos` (0.000u initial screen pop).
        2. Snap local player character state to Authoritative Server State at `clientTick`.
        3. Re-simulate physics forward from `clientTick + 1` to `currentTick` using recorded inputs (`isReplay = true` prevents duplicate network emissions).
        4. Overwrite history buffer for ticks `clientTick + 1`..`currentTick`.
        5. Freebody objects remain cleanly managed by `syncAuthoritativeObjects` to prevent object rewind jitter.

  [x] 8.3 Render Smoothing Dampener (Eliminates Visual Popping)
      - During rendering:
        `drawX = entity.position.x - visualOffset.x;`
        `drawY = entity.position.y - visualOffset.y;`
      - Decay visualOffset smoothly toward zero over 3 to 5 frames (~50ms - 80ms):
        `visualOffset.x *= 0.70;`
        `visualOffset.y *= 0.70;`
      - Result: Physics hitboxes snap instantaneously and remain 100% accurate, 
        while the visible sprite glides smoothly without jitter or teleportation.
